# Remote Chat replay review — one confirmed integration blocker

**Finding:** a synchronous `admitted()` failure before consumer acceptance permanently suppresses admission notification on that delivery. A fresh observer can receive replay events without the admission callback required by the frozen core seam. Ordinary observer replacement **after accepted admission** is not itself defective.

## Failure, supported by the current API
1. Valid successful SSE headers identify the conversation/assistant. `remote-chat.ts:308–311` saves `ledger.admission` and the conversation before calling the first observer.
2. The observer throws **before** accepting/storing IDs or resolving its admission waiter. `:312–315` aborts delivery; `.completion` rejects `provider_error`; binding epoch remains active. Getter reports `admitted` because backend identity was validated (`:395–396`), correctly distinct from consumer acknowledgement.
3. `resume(freshObserver)` reuses the same POST path/body/key, without an unacknowledged cursor. Matching headers pass, but `first` is false; fresh `admitted()` is never invoked. Probe order is `[text_delta, done]`, not `[admitted, text_delta, done]`. The fresh waiter remains unresolved before **and after** successful replay completion.
4. This is a frozen-seam failure, not a stylistic callback preference: `/tmp/opencode/remote-chat-core-seam.md:55–58` permits synchronous validation failure, exposes messages/resolves admission only inside `admitted`, and explicitly requires a new waiter on resume while core is still unadmitted. Main's existing tests already make observer failures replayable for `event`/`cursor` (`packages/desktop/test/remote-chat.test.ts:276–302`); `admitted` is the uncovered case.

The public enum getter exposes **no IDs**. `.resume()` eventually returns `{admission,terminal}` (`remote-chat.ts:344–347`), but only after completion: the bounded probe holds the stream open after a text delta, when both result and new admission waiter are pending. Waiting for terminal IDs cannot restore header-time admission; a core observer rejecting unadmitted events would fail earlier. The old `.completion` remains rejected. There is no public early known-admission accessor to satisfy this seam.

## Controls and guard distinction
- **Previously accepted IDs:** core retains its aliases and needs no new waiter. A replacement observer receives `done`, result IDs match the retained IDs; no repeat `admitted()` is required for this existing successful-admission path. Probe preserves the current once-only behavior and passes.
- **Abort before headers:** delayed Fetch ignores cancellation; `session.clear()` rejects completion with `aborted`, emits zero admissions/events, rejects resume without another POST. Guard/transport wins; no missed admission to recover in that epoch.
- **Abort inside `admitted()`, then throw:** completion and resume reject `aborted`, not the consumer's raw error or a usable recovery. Zero projected events; one POST. `onResponse`'s broad catch creates `provider_error`, but `execute` catch/outer `run` recheck the account and preserve invalidation (`remote-chat.ts:226–239,348–353`; `remote-session.ts:66–73,187–193`). Getter may remain `admitted`; epoch must be checked first, as documented.
- Ordinary consumer throw leaves the account active and delivery resumable; therefore the abort controls do not justify suppressing its fresh admission notification. Replayed POST is byte/key/path-identical, not a new backend turn. No unsupported post-terminal callbacks were requested or tested.

## Minimal correction, contract tradeoff
Retain validated ledger identity before invoking consumer code. After every validated response/current-epoch guard, invoke `observer.admitted({ ...ids })` unconditionally: remove `const first = !ledger.admission` and its `if (first)`. No new transport request, ledger, endpoint or fresh key.

Define that callback as **idempotent header admission per delivery attempt**. Core accepts first IDs; on later notifications it verifies identical IDs, retains existing user/assistant records, resolves only a still-pending admission waiter. Header mismatches still fail before notification. This directly repairs fresh-observer recovery with the smallest state change.

This deliberately changes `packages/desktop/test/remote-chat.test.ts:245`: its three valid responses should produce **three equal admission notifications**, not one. Update that expectation only with this explicit callback contract; retain its one path/body/key and cursor assertions. Likewise, the passing replacement-observer control here would expect one notification on its new attempt. Do not silently waive once-only assertions.

If once-only **successful acknowledgement** is a hard requirement instead, keep `ledger.admission` plus a separate acknowledged flag, set only after synchronous callback success/current-epoch guard; retry notification until acknowledged. That preserves the existing count but adds state. **Do not simply move/clear `ledger.admission` after a callback:** losing already-validated IDs weakens replay mismatch protection; leaving `conversations` populated would also trigger the new-conversation duplicate guard (`:305–307`). No production fix applied.
