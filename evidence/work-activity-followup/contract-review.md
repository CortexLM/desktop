## Required scope corrections
1. Delivery lines 5/43 promise latest completed outcomes, but lines 9–13 erase an existing outcome whenever a later user/incomplete message exists. That is a current-last-turn projection, not the promised historical outcome view.
2. Prefer the smaller, clearer history contract: one **latest completed assistant turn** per selected root; `messages.findLast(m => m.info.role === "assistant" && Number.isFinite(m.info.time.completed))`. Retain its exact outcome/time while a follow-up runs; replace only when that follow-up completes. It describes a past turn, never current session status. This supersedes the prior report's last-message-only suggestion.
3. Scope copy: **“The latest finished turn from each of up to 40 recently updated Bot conversations.”** Empty copy must mean no finished turns within this bounded selection, not “No activity yet” when earlier/out-of-window activity exists. Remove “unread last message” from verification: no unread contract exists.
4. This also resolves a refresh mismatch: normal follow-ups in an already-titled session emit user/assistant `message.updated`, but no mandatory `session.updated` until completion (`packages/core/src/session.ts:192–199,218–220,329–330,465–470`). The candidate's terminal-only message refresh cannot reliably hide rows at follow-up start. Retaining past outcomes makes terminal refresh correct.
5. Root eligibility: `kind === "bot"`, no parentID, nonempty botID. Do not require the Bot still exists. Generic creation permits missing/arbitrary botID (`packages/schema/src/index.ts:487–496`; `core/src/session.ts:68–86`); Bot-specific creation validates linkage (`server/src/index.ts:128–132`). Child sessions inherit identity but are excluded (`core/src/session.ts:238–246`).
6. Change `act.missingBot` from **“Deleted Bot”** to **“Unavailable Bot”**. Even successful complete list absence cannot prove prior existence: arbitrary dangling IDs are accepted. Only use fallback after successful authoritative Bots read; failed/partial metadata reads remain Retry, never deletion evidence.

## Data / behavior constraints
- `packages/core/src/storage.ts:147–155` returns messages ordered ascending by ID, not completion timestamp; IDs are time-based (`schema/src/index.ts:12–18`). Use returned order to select the last eligible assistant, then sort chosen rows by persisted completion time and stable IDs. Do not invent an insertion/clock-correction ordering unavailable from the API.
- `core/src/session.ts:450–470`: `time.completed` exists for success, failure and abort; absent error means completed turn, `error.code === "aborted"` means Interrupted, remaining errors mean Failed. Permission rejection is not ordinary abort. No raw error.message or inferred tool/business success.
- Hard process loss may leave an assistant incomplete; retain a previous finished turn if present, otherwise omit. Scheduler startup repairs TaskRun documents, not those assistant messages (`core/src/scheduler.ts:116–121`); do not synthesize an interrupted conversation from idle/reload.
- Session summaries lack outcome/current-run state (`schema/src/index.ts:158–184`), but full message reads supply sufficient terminal timestamps/errors. No model/catalog/provider lookup is needed to read historical outcomes.
- Select roots before taking 40; sort session.time.updated descending with ID tie-break. This timestamp also changes on rename (`core/src/session.ts:99–114`), hence “recently updated,” not “40 latest completions.” Session/Bot lists are unpaginated (`storage.ts:133–141`, `bot.ts:19–21`); 40 bounds history-request fan-out, not list size or transcript bytes.
- Filter the bounded result by exact botID/type; cap does not expand per Bot. Duplicate names need distinct ID-backed options/selection, resolved current mascot metadata and useful visual distinction. Do not pass missing identities through `screens/work/common.tsx:81–89`, which can borrow the first Bot's mascot.
- Routine-created Bot sessions qualify once; TaskRun.taskID is a scheduler-record ID, never a conversation destination. Confirmed target: `screens/work/home.tsx:260–263` reads **id**; `common.tsx:18–20` requires `go("work-task", "", {id: session.id})`. Destination can show a newer running turn; feed row remains explicitly historical.
- Exact link works with deleted-Bot sessions, but existing target uses first-Bot fallback (`home.tsx:431–437`). Verify neutral attribution there before claiming deleted-Bot navigation; a narrow target correction may be needed, not a new feed route.
- Subscribe before reads; invalidate snapshots on session deletion/updates and terminal message updates. Immediately retire a deleted ID so late history/list reads cannot resurrect it. On history 404, re-list: omit only confirmed absent ID; still-listed ID or failed re-list is retryable error, not silent loss.
- Retry reruns real session/Bot/history reads. Request generation + mounted/committed-owner guards must cover remount and canceled preview transitions; `state/live.ts:18–27` alone is not a full owner guarantee. Bot CRUD has no change event; remount/explicit refresh must reread metadata.
